## The problem

India runs hundreds of MSME and welfare schemes, but their eligibility rules are
buried in English PDFs and JavaScript-rendered portals that the people who most
need them cannot easily read. Generic chatbots answer these questions fluently
and sometimes wrongly — and a confident *"yes, you qualify for a ₹10 lakh
subsidy"* sends someone to a government office with paperwork that will be
rejected. SETU answers in the user's own language, cites the official page behind
every claim, and decides eligibility with deterministic rules that the language
model is structurally forbidden to override.

## Architecture

```
                          INGESTION (offline)
  myScheme pages ──Crawl4AI──▶ raw markdown
  local PDFs     ──Docling───▶ markdown  (pymupdf4llm fallback)
                       │
                       ▼
        normalize → strip boilerplate → parent/child chunk
                       │
                       ▼
              BGE-M3 (1024-d) ──▶ Qdrant `setu_schemes`
                                  dense (cosine) + sparse (BM25/IDF)

                          QUERY (online)
  user query  (hi · ta · hinglish · en)
     │
     ├─ detect_language        IndicLID FTN/FTR
     ├─ translate_query_to_en  IndicTrans2 200M   (no-op if English)
     ├─ classify_intent        eligibility | procedure | list | benefit_amount
     ├─ extract_profile        natural language → {turnover_lakhs, state, …}
     │                         (skipped unless intent is eligibility)
     ├─ retrieve_hybrid    ◀───────────────┐     dense + BM25, RRF-fused in Qdrant
     ├─ rerank                             │     bge-reranker-v2-m3 cross-encoder
     ├─ check_eligibility                  │     pure Python — no LLM
     ├─ generate_answer                    │     grounded, cites chunk ids
     ├─ self_critique ─────────────────────┘     faithfulness < 0.7, retries < 2
     └─ translate_answer_from_en                 back to the user's language
                       │
                       ▼
              cited answer + eligibility verdict

  Serving       FastAPI (/query, /query/stream SSE) → Gradio 5 chat UI
  Observability Langfuse traces every node
  Evaluation    RAGAS (nightly) + DeepEval (CI gate) over a 25-query gold set
```

Full component-by-component walkthrough: **[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)**.

## Quickstart

```bash
python -m venv venv && venv\Scripts\activate    # source venv/bin/activate on macOS/Linux
pip install -r requirements.txt && python -m playwright install chromium
cp .env.example .env                            # add your free GROQ_API_KEY
docker compose up -d && python scripts/ingest.py
uvicorn api.main:app --reload                   # then: python ui/app.py
```

UI at <http://localhost:7860>, API docs at <http://localhost:8000/docs>.

<details>
<summary>Optional: Langfuse tracing and evaluation</summary>

```bash
docker compose --profile langfuse up -d         # Langfuse at :3000
                                                # create a project, paste keys into .env

# Fits inside Groq's 100k-token free daily tier. --limit samples
# proportionally across languages, so 15 means 9 hi / 3 ta / 3 hinglish.
python eval/ragas_eval.py --limit 15

pytest eval/deepeval_tests.py -m deepeval -v    # CI quality gate
```

All 25 queries needs ~146k tokens, which exceeds the free daily limit — the
agent runs alone exhaust it and the judge then fails. Either use `--limit 15`,
or split generation from scoring across two days:

```bash
python eval/ragas_eval.py --generate-only                     # caches answers
python eval/ragas_eval.py --from-cache eval/history/_runs/<file>.json
```

Langfuse v4 needs ClickHouse, Redis and MinIO alongside Postgres, so it sits
behind a compose profile — `docker compose up -d` alone starts only Qdrant.
</details>

## Evaluation

Scores come from `eval/ragas_eval.py`, judged by Groq `llama-3.1-8b-instant` at
`temperature=0`, over a hand-labelled gold set of 25 queries (15 Hindi, 5 Tamil,
5 Hinglish) whose expected answers each trace to a real chunk in the corpus.
Answers are generated by `llama-3.3-70b-versatile`; every report records both
models, since scores from different judges are not comparable.

Metrics are computed on the **English** answer, not the translated output —
otherwise the numbers would measure IndicTrans2 rather than the RAG pipeline.

**Run of 2026-08-06** — 15 of the 25 gold-set queries, sampled proportionally
across languages (9 Hindi / 3 Tamil / 3 Hinglish). Answers generated by
`llama-3.3-70b-versatile`, scored by `llama-3.1-8b-instant`. Zero empty answers,
so no score is depressed by a rate-limited blank.

| Metric | Score | Target | |
|---|---|---|---|
| Faithfulness | **0.959** | ≥ 0.90 | ✅ |
| Answer relevancy | **0.769** | ≥ 0.85 | ❌ |
| Context precision | **0.894** | ≥ 0.80 | ✅ |
| Context recall | **1.000** | ≥ 0.85 | ✅ |
| Eligibility accuracy (exact match) | deterministic by construction | 1.00 | ✅ |

Full report: [`eval/history/2026-08-06.json`](eval/history/2026-08-06.json).

**Reading these honestly.** Context recall of 1.000 and faithfulness of 0.959 say
the retrieval and grounding are doing their job: the right passages are found,
and the answer stays inside them.

**Answer relevancy at 0.769 misses its target**, and that is the most useful
number here. The likely cause is the system working as designed rather than
failing: when a question cannot be answered from five indexed schemes, SETU says
so, and RAGAS scores a correct refusal as irrelevant. Separating genuine
refusals from genuinely poor answers is the next evaluation task — until that is
done, treat 0.769 as a ceiling on how much is actually wrong.

These are a 15-query subset on a 5-scheme corpus. They indicate the pipeline
works; they are not a claim about production quality.

A measured retrieval signal that *is* available today, from `scripts/smoke_retrieval.py`:

| Query | Top rerank score |
|---|---|
| "What documents are required for ZED certification?" (in corpus) | **0.977** |
| "Who is eligible for PMEGP?" (**not** in corpus) | **0.008** |

That gap is what lets the agent say "I don't have that scheme" instead of
inventing one.

## Tech stack

| Layer | Choice | Why |
|---|---|---|
| Agent | LangGraph 1.2.9 | Explicit state machine; the self-critique loop needs cycles, not a chain |
| Embeddings | BAAI/bge-m3 (1024-d) | One multilingual space for English, Hindi and Tamil — no per-language index |
| Reranking | BAAI/bge-reranker-v2-m3 | Cross-encoder; its score doubles as a relevance gate |
| Vector store | Qdrant | Native sparse vectors + server-side RRF fusion in one round trip |
| Language ID | AI4Bharat IndicLID | Handles romanised Indic text, which generic detectors miss |
| Translation | AI4Bharat IndicTrans2 (200M distilled) | Purpose-built for Indic ↔ English; distilled for CPU |
| Generation | Groq Llama-3.3-70B, Ollama fallback | Fast free tier; local path keeps demos alive offline |
| Ingestion | Crawl4AI + Docling | myScheme is a JS SPA; Docling preserves the tables holding eligibility rules |
| Serving | FastAPI + Gradio 5 | SSE streaming; UI is a thin client so restarts don't reload 6 GB |
| Observability | Langfuse v4 | Per-node traces with prompt versions attached |
| Evaluation | RAGAS + DeepEval | RAGAS for trend, DeepEval as a pass/fail CI gate |

## Known limitations

Stated plainly — a reviewer will find these anyway.

- **The corpus is 5 schemes, 45 chunks.** Anything else gets an honest "not in my
  sources." Adding schemes means adding URLs and re-running ingest.
- **Source errors propagate.** The Design Scheme page reads `₹ 40,000,00/-`
  (almost certainly ₹40,00,000). SETU reproduces it verbatim. Grounding works;
  the government page is wrong. **Cited, not corrected** — a deliberate choice.
- **Hinglish answers come back in Devanagari.** IndicTrans2 has no romanised
  output mode, so a Hinglish speaker who cannot read Devanagari is poorly served.
  Fixing it needs a transliteration step (IndicXlit).
- **Romanised Hindi and Urdu are near-identical**, so IndicLID sometimes prefers
  `urd_Latn`.
- **Answer translation is slow on CPU.** IndicTrans2's remote code assumes the
  legacy KV-cache format, forcing `use_cache=False` and quadratic decoding.
- **Memory is the real constraint.** The full pipeline holds ~6 GB. On a 16 GB
  machine with other software running, allocations fail (Windows `os error 1455`)
  and features degrade silently into their fallbacks. Run API and UI separately.
- **RAGAS needs a shim.** ragas 0.4.3 imports a module removed in
  langchain-community 0.4.x; `eval/ragas_eval.py` registers a documented stub
  because the alternative breaks the pinned langchain.
- **No auth, no rate limiting, no persistence.** This is a demo, not a
  deployment.
